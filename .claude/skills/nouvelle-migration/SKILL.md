# Écrire une migration Flyway

## 1. Choisir le dossier et le numéro

| Contenu | Dossier | Numéro |
|---|---|---|
| Schéma, données de référence (production comprise) | `backend/src/main/resources/db/migration/` | le suivant après la plus grande version de ce dossier, **sous 100** : `V<n>__` jusqu'à `V99`, puis `V99_1__`, `V99_2__`… (voir ci-dessous) |
| Données de démonstration (profil `dev` seulement, noms fictifs) | `backend/src/main/resources/db/demo/` | le suivant après le plus grand `V1<nn>__` |
| Migration qui charge des fichiers (images…) | `backend/src/main/java/db/migration/` (classe Java) | même suite que le SQL de `db/migration` |

```bash
ls backend/src/main/resources/db/migration backend/src/main/java/db/migration | grep -o '^V[0-9_]*[0-9]' | sort -V | tail -1
ls backend/src/main/resources/db/demo | sort -V | tail -1
```

**Après `V99`** (décision Tech, 2026-10-21, relances CACI) : les numéros
≥ 100 restent à la démo (`db/demo`, profil `dev`). Le schéma continue en
sous-versions Flyway : `V99_1__…` (version 99.1), puis `V99_2__…`,
`V99_3__…` ; Flyway les ordonne entre 99 et 100, donc avant la démo en `dev`
et à la suite de V99 en production. Même règle pour une migration Java
(`V99_2__…` dans `backend/src/main/java/db/migration/`). Ne pas prendre
`V130__…` dans `db/migration` : les suites schéma et démo s'entremêleraient.

Nom : `V<n>__<description_en_snake_case_francais>.sql` (ou `V99_<n>__…`). En-tête en commentaire :
ce que fait la migration et pourquoi (même style que les voisines).

## 2. Règles

- **Ne jamais modifier une migration déjà sur `origin/master`** : le hook
  `.claude/hooks/proteger-migrations.sh` le refuse. Corriger = migration suivante.
- **SQL compatible H2 (dev, tests) et PostgreSQL (production).** Éviter les types
  et fonctions propres à l'un : `BIGINT GENERATED BY DEFAULT AS IDENTITY`,
  `VARCHAR(n)`, `TEXT`, `BOOLEAN`, `DATE`, `TIMESTAMP` ; pas de `SERIAL`, pas de
  `ON CONFLICT`, pas de JSONB. Regarder comment les migrations voisines font.
- **Colonne ajoutée à une table remplie** : nullable, ou `DEFAULT` + `NOT NULL`
  dans la même instruction ; reprendre les lignes existantes par un `UPDATE` si
  la règle métier l'exige.
- **Entité auditée par Envers** (`@Audited`) : la table `<table>_aud` reçoit les
  mêmes colonnes, dans la même migration (méthode dans `.claude/rules/audit.md`).
- **Données personnelles** : jamais de donnée réelle, ni en démo ni en
  production ; aucun champ de santé (« Données personnelles » de CLAUDE.md).
- **Démo** : si la fonctionnalité a un écran, ajouter des données de démo
  (`db/demo`) qui le rendent visible ; les vidéos et la démo en dépendent.

## 3. Tester (TDD)

- Un test qui échoue sans la migration (entité ou requête qui lit la colonne),
  puis la migration.
- Migration qui transforme des données existantes : un test qui rejoue Flyway
  jusqu'à la version précédente, remplit, puis applique la nouvelle (modèle :
  `MigrationParticipantLieTest`).
- `cd backend && mvn test` entier avant le commit : toutes les migrations sont
  rejouées sur une H2 neuve.

## 4. Documenter

Citer la migration (`V<n>`) dans le fichier `.claude/rules/<domaine>.md`
concerné si elle porte une décision.
